## Source/route surface audited

In `cloudflare/workers/gst-desk-preview/worker.js` and imported modules:
- `/api/state[/*]`, `/api/returns/summary`, `/api/meesho/summary` invoke `authorize()` before D1 handling.
- `/api/overview`, `/api/invoices[/*]` invoke `authorize()`.
- `/api/shipping/*` invokes `authorize()`.
- `/api/valmo/track` invokes `authorize()`, validates input and has an upstream timeout; third-party carrier lookup is not a documented official integration.
- `/api/catalogue/meesho` public page extraction is read-only but authentication needs exact route-flow review: this handler appears **before the generic fallback `authorize()`**. Inspect intent and threat model before any deployment.
- `state-api.mjs` verifies signed Cloudflare Access JWT (issuer/audience/expiry), compares email with `GST_OWNER_EMAIL` and checks D1 membership `role='owner'` for `GST_BUSINESS_ID`.
- Consequently **the separate spouse email login is not yet enabled** by the code shown; two actual authorized accounts are a future gate.
- State writes require same-origin request header `X-GST-Desk-Write: 1` and revision checks; overview and shipping tests exercise owner business scope.
- Actual independent-browser persistence, complete auth probing, large-file importer, GSTR-1 JSON schema, and rollback are **NOT** independently tested on live devices.

## Known deficits and deployment gates

1. **BACKUP FIRST:** Export authenticated production D1 data via safe owner-controlled backup, verify encrypted storage/restore on *isolated local or staging D1*, never overwrite the production DB during a rehearsal. Live backup was NOT performed here.
2. Audit actual deployed `gst-desk-preview` source against GitHub `main` and exact route/per-path auth matrix; manually test no-auth access and per-business isolation.
3. Confirm separate spouse email and add both identities securely using an approved Cloudflare Access allowlist, D1 user/membership and server-side email allowlisting; never grant access by client-supplied business ID.
4. Two-device reload test with synthetic records after approved backup.
5. Existing migration filenames `database/migrations/0002`–`0008` must not be overwritten or reused. Determine next available revision before introducing R2 schema.
6. Draft PR #1 and #6 are **not merged**; the relay source from #6 is deployed separately. Do not conflate deployment of the isolated relay with deployment of GST Desk application features.
7. Do not create/bind an R2 bucket until quota reservation, finalization, orphan reconciliation, and Class A/B operation metering are tested atomically in staging. Normal uploads must fail closed; cost alerts alone are insufficient.
8. Full QRMP tax validation, RTO fee evidence, official GST schema/filing compatibility and multidevice acceptance remain pending.
